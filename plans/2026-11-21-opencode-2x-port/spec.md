# Port the repository to OpenCode 2.x

[Issue #4](https://github.com/sflandergan/open-code-permissions/issues/4) · Target: [OpenCode v2.3.2](https://github.com/anomalyco/opencode/releases/tag/v2.3.2)

## Scope

The checkout and its published permission tooling run on v2.3.2. Convert repository-owned OpenCode configuration and agent definitions, preserve the agents’ effective protections and workflow, and remove the custom Mistral provider, its plugin, and its local setup references. The release includes the `permission-optimizer` recorder, both published skills, and the native copy-in `opencode-permissions` agent. Release automation, consumer-wide configuration conversion, managing saved approvals or managed `policies`, and running the new release on 1.x are out of scope.

## Recording and storage

- Record one observation per permission request, with its action, ordered requested resources, reply, completion, and observation origin. The request’s location supplies the worktree and repository identity; a correlated tool completion supplies the agent. Keep unknown facts unknown. Handle duplicates and early facts without overwriting known facts; require matching session/call and agreement of known message IDs. A tool call may have multiple observations.
- Record the `once`, `always`, and `reject` outcomes OpenCode reports. Count requests, not user clicks. The stream does not distinguish explicit replies from automatic resolutions or shutdown rejects; display these as observed outcomes, without guessing who answered. Preserve the historical interpretation of legacy derived decisions. For non-web actions, a successful `once` or `always` can qualify for its requested resource. For webfetch, retain `always` in history but use only `once` as recommendation evidence. All qualifying operational evidence requires successful completion, a known repository identity, and a known agent. Shell success requires a final zero exit code; a hook error is failure even without an exit code. A background acknowledgement or missing result is incomplete.
- Persist no saved patterns, raw payloads, tool arguments, output, or arbitrary metadata. Failures produce actionable diagnostics without interrupting OpenCode. Unload stops the observation subscription, drains in-flight work, and closes storage.
- Keep the database path, its override, and 30-day retention from last lifecycle activity. Under [ADR 0001](../../docs/adr/0001-plugin-owned-observation-schema.md), the recorder migrates schema 4 to 5 in one transaction, preserving observations and requested values. Store the OpenCode major version as integer `1` for legacy history or `2` for new 2.x observations. The reader only accepts schema 5, opens it read-only, and reports expected and found versions and the remedy on mismatch. A failed migration leaves the original database unchanged.

## Inspection and edits

Use the runtime’s `debug agents` output for agent IDs and ordered effective `action`/`resource`/`effect` rules; preserve order and duplicates. Use `debug config` and source declarations to establish rule origins. Keep uncertain origins visible and ineligible for editing. The report describes configured per-agent policy; session rules, saved approvals, and separate managed policies may affect individual requests. Recognized legacy declarations may be inspected but not edited.

For every edit, verify the native source is repository-owned, show the complete ordered diff and affected scope, and obtain explicit owner confirmation. Recheck source bytes and affected effective rules immediately before mutation. On any change, prepare a new diff and obtain fresh confirmation. After applying, re-inspect all affected agents; report success only if the intended effective change and remaining rules are verified. Report the changed file on failure. The optimizer remains advisory and the inspector retains its output-file workflow.

## Recommendations

- Show history and qualifying approval counts by numeric OpenCode major version. Treat legacy history as context unless a qualifying legacy `skill` request resolves to the same skill under the same identifier for the selected agent. Legacy shell, webfetch, and unknown actions never justify a new 2.x allow.
- For webfetch, require successful 2.x `once` approvals for at least two distinct requested URLs in one scope. On ordinary hosts use an exact HTTP(S) origin (`scheme://host[:port]/*`); for GitHub use an exact user or organization namespace on `https://github.com` (`https://github.com/<owner>/*`). Never fall back to a GitHub-wide rule. Withhold broader rules for known multi-tenant hosts without supported boundaries; describe the supported and excluded hosts in a dedicated extensible Markdown reference. The runtime matcher must cover the original requested URLs with the proposed pattern. Explain what new paths and queries it admits, require role justification, and preserve applicable denies and narrower asks. A saved `*` adds no URL evidence. HTTP redirects are checked for denies but do not trigger a fresh ask at each hop; a URL rule does not confine redirects to its scope.
- For shell redirection, show two variants against the existing ordered rules: preserve the current redirect policy and explain the command allow’s effect; or propose an explicit command-scoped redirect change and explain its effect. Work with absent guards and deny-only path exclusions. Preserve unrelated denies. Place unconditional command bans after overlapping allows and path rules. Allow after a broad deny only for a deliberately narrow exception.

## Acceptance

Use hermetic captured runtime fixtures, isolated SQLite, focused TDD, and whole-suite/package gates. Verify ambiguous origins, stale confirmation, migration rollback and reader compatibility, completion correlation, URL boundaries, and both shell redirect variants.

Run the pinned runtime outside the hermetic suite. Verify the actual checkout’s configuration and workflow, local and packed-package recorder discovery, a real approved prompt with successful completion in history, a confirmed URL-rule edit with verified order and origin, loopback HTTP redirect behavior, and recorder cleanup. The owner’s regular profile may provide a compatible model; never select the removed Mistral adapter. Use a disposable project for interactive cases and separate observation databases. Record the exact runtime and all acceptance results. Document explicit installation, the copy-in agent refresh, preservation of the earlier `external_directory` caution, database backup, and rollback by restoring that backup.
